## 使用约束

- V2 已确认并完成紫幕拆分；动态文字、数值和进度继续交给 Godot 预置 `Label / ProgressBar`，不得烘焙进最终面板贴图。正式 HUD 场景仍需在测试场景通过人工评审后再替换。
- 正式联机 HUD 禁止重新加入香盘、计时香、回合香或用燃香长度承载计时；唯一正式计时语义为顶部 `TurnStatusBar`。
- `multiplayer_match_hud_region_map_v1.png` 只定义区域责任和相对布局，不冻结像素尺寸、最终节点名、主题皮肤或数据接口；正式场景仍应由容器响应式布局，不得按图中坐标硬编码所有控件。
- 两张 HUD V1 图是分别独立生成的布局候选，不得拼接为同一运行时画面；前者只服务联机对局，后者只服务关卡闯关。二者尚待项目所有者确认，不代表最终 UI 已冻结。
- 两张 HUD 图中的棋盘格线、棋子位置、数值、图标和生成式文字只用于层级评审；正式实现必须继续使用项目精确 `9×24` 交点、观察者安全数据和预置 `Control / Container / Theme`，不得把整图作为可交互背景。
- 图中文字、棋子字形、棋盘线条和印章均为生成式概念内容，不得直接拆出作为可发行生产母版。
- `loading_transition_reference_v1.png` 同时展示加载态与失败组件只是为了单图评审；正式运行时二者必须按状态互斥。背景、雾带、兵符、状态、进度和失败面板应拆为预置 `Control` 层级，主要动效使用可中止、可重播并支持减少动态效果的 Tween。
- 正式棋盘仍需使用项目精确的 `9×24` 交点矢量资源，不得照抄概念图中的格线和残局位置。
- Godot 实现继续使用预置 `Control / Container / Theme`；概念图只提供视觉目标，不承担交互、焦点或规则状态。
- 对局 HUD 经确认后，应以本图为风格参考重新生成透明背景组件并制作九宫格，不直接裁切带战场底色、棋子或生成式图标的像素。
- V5 是不含 UI 的背景母图；正式菜单、焦点状态和版本信息应在 Godot 预置 `Control` 场景中独立叠加。
- V6 烘焙了单行进入提示，仅作为启动画面效果示意；正式实现仍优先以预置 `Label` 叠加相同文案，便于呼吸动画、输入切换和本地化。
- V7 的降噪目标是减少高频视觉噪声，不改变构图和关键识别；正式导出避免再次锐化或添加胶片颗粒。
- `level_gameplay_hud_concept_v1_t03_field_lattice.png` 中的文字、棋盘坐标、战术路径和机制高亮均为概念内容；正式实现必须复用 `match_hud_v2` 的预置节点骨架，并由关卡安全数据驱动 `TutorialOverlay`、目标状态、提示按钮和棋盘覆盖层，不得直接将整张概念图作为可交互 HUD。
- 关卡内部 HUD 的当前方向以 V4 为准：严格沿用联机对战 `1280×720` 构图，不保留独立“教学提示”大面板，也不扩展画布；复用右侧 `ObjectiveEvents`／“战局与行动”预置节点，在原右侧信息列内承载关卡、目标、步骤、当前操作、提示／状态与必要教学操作按钮，不新增第二块常驻信息板。
